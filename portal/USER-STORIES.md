# VSMC 自助式 VM 申請入口 — User Stories

> 開發依據。每一則 story 都要能對應到後端 vRA 的一個實際行為，或前端的一個畫面。
> 後端 vRA 已驗證的能力見 `vrablueprint` repo 的 `docs/api-runbook.md`。

## 角色

| 角色 | 說明 |
|---|---|
| **申請人 Requester** | 製程 / 設備 / IT 工程師，需要一台 VM |
| **主管 Approver** | 申請人的主管，負責簽核 |
| **平台管理員 Platform Admin** | 維護選單與對應關係（叢集 / 網段 / size / OS） |
| **稽核 Auditor** | 資安或稽核單位，需要查得到誰開了什麼機器、用途為何 |

---

## Epic 1 — 身分與登入

| ID | User Story | 驗收條件 |
|---|---|---|
| US-01 | 身為**申請人**，我要用公司 **AD 帳號**登入，不必另記一組密碼 | 以 AD 帳密可登入；停用的帳號無法登入 |
| US-02 | 身為**申請人**，我希望姓名 / 部門 / Email / **員工編號**自動帶入，不要我手填 | 表單不出現可編輯的申請人與工號欄位；送出的申請掛在登入者身上 |
| US-03 | 身為**稽核**，我要確保申請人與員工編號**無法被冒用** | 兩者皆由後端 session 決定，前端傳什麼都無效 |

> 設計含意：`requester` 與 `employeeId` 一律由中介層從 session 填入，**不接受前端傳入**。
> 員工編號從 AD 的 `employeeID` / `employeeNumber` 屬性讀取（不同 AD 架構欄位不同，兩者都試）。

## Epic 2 — 申請機器

| ID | User Story | 驗收條件 |
|---|---|---|
| US-04a | 身為**申請人**，我要填**申請單號**，把這台機器對回既有的 ITSM 工單 | 單號為必填；格式錯誤在送出前就擋下 |
| US-04 | 身為**申請人**，我要選**作業系統** | 下拉顯示可用 OS；只列平台管理員開放的項目 |
| US-05 | 身為**申請人**，我要選**規格 size**，而且看得到每一級是幾核幾 GB | 下拉顯示 `small (1C/2G)` 這種帶規格的標籤 |
| US-06 | 身為**申請人**，我要選**部署叢集** | 下拉顯示可用叢集 |
| US-07 | 身為**申請人**，我要選**網域區隔（MES / FDC / OA）** | 下拉三選一；決定機器落在哪個網段 |
| US-08 | 身為**申請人**，我要填**用途**（代碼＋備註） | 用途為下拉代碼，備註為自由文字 |
| US-09 | 身為**申請人**，我要在送出前看到**申請摘要** | 顯示所有選項與換算後的規格 |
| US-10 | 身為**申請人**，送出失敗時我要看得懂**原因** | 顯示後端具體錯誤，例如「找不到符合 zone:fdc 的網段」 |

> 🔴 **US-07 是半導體環境的硬性資安要求**，不是分類標籤 ——
> MES / FDC / OA 決定網段隔離，選錯等於違反隔離政策。
> 技術上對應 fabric network 的 `zone:*` tag ＋ 藍圖的 network `constraints`，
> 已實測：沒有對應網段時 vRA 會直接擋下並回明確訊息。

## Epic 3 — 進度與交付

| ID | User Story | 驗收條件 |
|---|---|---|
| US-11 | 身為**申請人**，我要看到申請的**目前狀態** | 顯示 建置中 / 完成 / 失敗 |
| US-12 | 身為**申請人**，完成後我要看到 **VM 名稱與 IP** | 交付頁顯示機器名稱、IP、規格 |
| US-13 | 身為**申請人**，完成或失敗要**通知我** | Email 或站內通知 |

> 設計含意：vRA 的部署是非同步的，中介層要自己輪詢並提供狀態端點，
> 不要讓瀏覽器直接對 vRA 長輪詢。

## Epic 4 — 我的機器

| ID | User Story | 驗收條件 |
|---|---|---|
| US-14 | 身為**申請人**，我要看到**我申請過的所有 VM** | 只看得到自己的（或自己部門的） |
| US-15 | 身為**平台管理員 / 稽核**，我要能依**用途 / 環境 / 網域**篩選 | 可依 tag 篩選出清單 |

> 設計含意：需要篩選的維度必須放進 vRA 的 `tags`（實測 `tags` 可用 `$filter` 查詢，
> 自訂 properties 讀得到但不能 filter）。
> vRA 端所有部署都掛同一個服務帳號，**「誰申請的」必須由中介層自己記錄**。

## Epic 5 — 管理與稽核

| ID | User Story | 驗收條件 |
|---|---|---|
| US-16 | 身為**平台管理員**，我要能新增一個叢集 / size / OS / 網域選項，**不必改藍圖** | 於 vRA 加 mapping 或打 tag 即生效 |
| US-17 | 身為**稽核**，我要查得到**誰、工號、哪張單、何時、什麼用途**申請了哪台機器 | 可依申請人或**單號**反查機器清單 |
| US-18 | 身為**平台管理員**，我要知道機器的**使用期限**並能提醒回收 | 記錄到期日並可產出到期清單 |

> 已實測：size → flavor mapping、OS → image mapping、cluster → compute tag、
> zone → network tag。四者新增選項都**不需要修改藍圖 YAML**。

## Epic 6 — 可用性與安全（對應 Load Balance 需求）

| ID | User Story | 驗收條件 |
|---|---|---|
| US-19 | 身為 **IT**，我要能跑**多個網頁執行個體在負載平衡之後**，單一節點故障不中斷服務 | 任一節點停止，服務仍可正常登入與送單 |
| US-20 | 身為 **IT**，我要**任一節點都能處理任何請求**（無 sticky session 需求） | 應用**無狀態**：session 以簽章 token 保存，不存在單一節點記憶體 |
| US-21 | 身為**資安**，vRA 的憑證**不得外流到瀏覽器** | 瀏覽器只拿得到本站 session；vRA token 僅存在於中介層 |
| US-22 | 身為 **IT**，我要有**健康檢查端點**供負載平衡器探測 | `/healthz` 回應節點與後端 vRA 連線狀態 |

> 🔴 US-20 是 LB 能不能成立的關鍵：**應用必須設計成無狀態**，
> 否則加了負載平衡器也只能綁 sticky session，節點掛掉使用者就被登出。

## 半導體環境的特別注意事項

1. **MES / FDC / OA 網段隔離**是資安政策，屬於放置決策（`constraints`），不是屬性標籤。
2. **稽核留痕**：客戶稽核 / ISO 情境下，每筆申請的輸入與結果都要留存。
3. **代申請**：申請人可能不等於機器實際擁有者，兩者要分成不同欄位。
4. **廠區 site**：若跨廠區，`site` 同樣屬於放置決策而非標籤。
